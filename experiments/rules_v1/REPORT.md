# 规则预演 v1 · 不生成边，直接找交叉点（刘线，2026-10-12）

> 实验，不上线：街区页、账本目录一字未改；v0 目录只读复用（`rules_v0/data.py` 的加载器、`cross.py` 的打分常量）。
> 同一台沙箱（2 核、8 GB）上与 v0 对照。v0 的时间是本轮重新跑出来的，不是抄 v0 报告。

## 1. 一句话结论

**v0 的交叉点一个不差地找回来了，干山从 28.5 秒降到 0.89 秒（算交叉点的部分），全城从 154 秒 CPU / 423 MB 降到 2.9 秒 / 130 MB；单户「此刻的自我网」按需现算平均 1.5 ms（全城 2.3 ms，最慢 4.9 ms）。**
样本 126 / 干山 7,035 / 全城 25,494 个交叉点，与 v0 调参版逐条核对：同一对人家、同一组模式、同样的命中年份、同样的分数，前 8 名和前 60 名完全一致（三个范围都是 0 差异）。
一条没完全达标：干山如果把 Python 启动 + 导入 numpy/scipy（0.26 秒）和写结果文件也算进去，整条命令墙钟是 1.37–1.40 秒；瓶颈见 §7。

## 3. 做了哪几项优化，各省了多少

干山（compat 模式）开发过程中逐步测得的时间：

| 步骤 | 做法 | 干山时间 |
|---|---|---|
| v0 | 每年把 13 条规则的边全部生成成 Python 元组，再在边上找模式 | 28.5 s |
| ① 不生成边 + 状态矩阵 + KD 树 | 每户每年的状态（在不在、几口人、成年男人、孩子、丧事、12–15 岁男孩）预计算成矩阵，每年切一列；交叉模式 = 「承载关系 ∧ 户属性条件」，用 cKDTree 只在近邻里找；背景类关系（面包/信仰/同行/运水人）只给交叉点两端按需查 | 5.1 s |
| ② 按需查的部分向量化 | 交叉点两端的「是不是彼此 k 近邻」一次批量查；恩主改为每户取最近 24 个候选（不够才退回整球） | 1.43 s |
| ③ 命中留成 numpy 数组 + 打分缓存 | 不逐条造元组；「账本大事贴近度」按 (年, 主题, 是否阿里乌派) 缓存 | 1.17 s |
| ④ 房东分配 | 每条街的有房户按搬入年排好，满员就从街表删掉；没街名的租户批量球查询、候选预排序 | 1.12 s |
| ⑤ 增量：同一口水 | 组内 4 近邻逐年只重算受影响的户（新来的、近邻走了的、新来户落在其第 4 近距离以内的）——每年平均只重算 9.6% 的户（干山 7,441 / 77,123 户·年），结果与从头算完全相同 | 1.07 s |
| ⑥ 最便宜的条件先筛 | 交叉点两端先看是否同派/同街同行/同炉、是否在半径内，再查近邻；模式本身已蕴含的规则（同水异粮蕴含「同一口水」「面包」）不再查 | 0.97 s |
| ⑦ 同乡候选表进缓存 | 「同籍贯、早 1–8 年来、300px 内」只依赖坐标和搬入年，一次算好（干山 85,150 条候选）；每年只找第一个还在住的 | 0.89 s |
| v1 模式 | 去掉运水人边（只留「离水远」这个户属性） | 0.84 s |

**最后一版的时间花在哪**（干山 / 全城，秒）：房东分配 0.11 / 0.29，同行对头 0.08 / 0.31，恩主分配 0.08 / 0.25，同一口水（增量）0.07 / 0.29，学徒 0.05 / 0.19，喝哪口水 0.04 / 0.12，交叉点两端按需查背景关系 0.22 / 0.72，打分 0.12 / 0.48。

**等价的细节**：v0 有些「同距离时谁先」取决于它的网格遍历顺序（井按 140px 格、户按 120px 格、同乡按 150px 格；炉取列表里第一个）。全城的合成坐标是整数，同距离很常见——不照 v0 的顺序打破平局，全城第一版有 128 处差异（多/少 98 个交叉点，其余是年份或分数）；照着做后 0 差异。干山、样本是浮点坐标，一开始就 0 差异。

**试过但没用的**：同行对头按 (街, 行当) 组缓存做增量，85% 的组可沿用，但 Python 逐组比签名的开销抵掉了收益，已撤回；房东分配「在住户集合与街没变就沿用上一年」的增量写了，但 21 年里一次也没命中（每年总有人家搬来或死绝，房东分配又是全城一个顺序贪心）。

## 4. v1 模式：两处规则改动

1. **运水人边去掉**，只留户属性（是不是运水人、离水远不远）。它只在打分里贡献「同一口水」这条规则名，而同水的邻居本来就有：干山只有 54 个交叉点的分数因此变了（全城 62 个）。「运水人摊上公家的事」只看户属性，不受影响。
2. **「学徒拜异派师傅」降权**：「工钱与学徒」只算半条，多模式加分 1.5 → 0.75。交叉点集合不变（7,035），只是排序变：干山前 100 名与 compat 重合 80 个；前 8 名留下 4 个（14228/14736、13550/13969、12339/12484、12129/3103），换进来 4 个不带学徒的（6464/6616 债主欠债同街 + 同水异粮，10019/12446，15196/15878，2672/3426）。

| 只要前 4 条 平均 / p95 | 0.10 / 0.19 ms | 0.41 / 1.53 ms | 1.33 / 2.76 ms |
| 户均关系数（最多） | 16.9（32） | 21.9（42） | 19.3（39） |
| 与 v0 全量边逐户逐类核对 | 80 户全同 | AF51/55/57/60/62/65/70 各 250–400 户，**全同** | AF55 400 户，**全同** |

核对的类：同一口水、面包、信仰、同乡、同行同街、同行对头、学徒、施舍、拆房/凑铜板/征工、兵营（含反向：别人把我算进他的 k 近邻）；房东、恩主、债另在干山 AF51/55/60 和全城 AF55 核对，也全同。

做法：每户只在自己所在的组里现算（同一口水 = 喝同一口井的在住户；信仰 = 同派 180px 内；面包 = 同炉有房户；同行 = 同街同行），一个小 KD 树查组内近邻和反向近邻；同乡链读预计算的候选表；房东/恩主/债这三条是全城一个顺序贪心，单户算不出来，所以读批量算时存下的分配区间（户均 2.1 条）。

**移植到浏览器 JS**：可行。要下发的是每户不变属性 + 每户每年 1 字节状态位 + 强关系，背景关系全部在浏览器里从坐标现算：

## 7. 骨架去重

**骨架签名** = 模式组合 + 角色关系 + 结局类型（`skeleton.py`）。
- 角色关系：两户之间最强的制度关系（房东-租户 > 债主-欠债 > 恩主-门客 > 师傅-学徒 > 同乡先后 > 同行对头 > 只是邻居）· 有房/租组合 · 同行/异行；单户 × 机构记「户×机构」。
- 结局类型：交叉点最后一年之后——拆房 / 一家死绝 / 换了人家 / 有人去世后不再成立 / 条件消散（孩子长大、不再缺男丁）/ 延续到 70 年。

**干山分布**（v1 模式，7,035 个交叉点）：不同骨架 285 个（v0 的旧签名只分出 124 个），前 5 种占 37%：

| # | 骨架 | 个数 | 占比 |
|---|---|---|---|
| 1 | 同水异粮 · 只是邻居·有房×租·异行 · 有人去世后不再成立 | 1,233 | 17.5% |
| 2 | 同乡异信 · 同乡先后·有房×有房·异行 · 延续到 70 年 | 457 | 6.5% |
| 3 | 同水异粮 · 只是邻居·有房×租·异行 · 条件消散 | 383 | 5.4% |
| 4 | 同乡异信 · 同乡先后·租×租·异行 · 延续到 70 年 | 308 | 4.4% |
| 5 | 正统房东·阿里乌派租户 · 房东-租户·有房×租·异行 · 延续到 70 年 | 224 | 3.2% |

结局分布：有人去世后不再成立 2,636、延续到 70 年 2,157、条件消散 1,718、一家死绝 502、拆房 22。头部前 8 名的角色全是「房东-租户·有房×租·同行」（7 个）和「债主-欠债」（1 个）——旧签名看不出来的重复。

**三条改法（只提议 + 小测，没改规则）**：

| 改法 | 交叉点 | 不同骨架 | 前 5 占比 | 高分（≥12）对保留 |
|---|---|---|---|---|
| 现状 | 7,035 | 285 | 37.0% | — |
| ① 转折触发：同水异粮 / 同井施舍分线只在丧事或缺男丁「新近 3 年内开始」时成立；同乡异信只在 51–53 年或后来那家刚到的 3 年内成立 | 6,757 | 284 | 34.8% | 256/258 |
| ①a 只改同水异粮那一半 | 6,856 | 275 | 37.9% | 256/258 |
| ② 一户只认一个：同一年里一户没面包的人家只跟分数最高的那一家有面包的邻居构成同水异粮 | **5,150** | 282 | **27.5%** | 255/258 |
| ③ 选故事时骨架配额：分数 − λ·log2(1 + 前面已有的同骨架数) | 不变 | 前 100 名里 61 → 86（λ=1）/ 94（λ=2） | 前 100 名里 28% → 12% / 11% | — |
| ③' 配额只按「角色关系」那一段，λ=2 | 不变 | 前 100 名 68 | 前 100 名 20% | 前 8 名角色从 2 种变 6 种，换掉 4 个 |

- ② 最有效：同水异粮里大量是「一户缺男丁的租户」同时对四五家有房邻居各算一次，压成一家后同一个骨架从 17.5% 降到 4.9%，高分对几乎不丢。
- ① 让「同乡异信」从「延续到 70 年」挪到「条件消散 / 有人去世」，但同水异粮那一半效果很小——苦大多本来就是新近开始的（丧事当年就算）。
- ③ 不改交叉点，只改挑哪几个写故事；按完整签名配额对前 8 名没影响（前 8 本来就互不相同），按「角色关系」配额才能把前 8 名从清一色「房东-租户」拉开。建议 ② + ③'。

## 8. 已知问题

1. **干山墙钟略超 1 秒**：算交叉点 0.84–0.89 s 达标；加上 Python 启动 + 导入 numpy/scipy 0.26 s、写全部交叉点文件约 0.2 s，整条命令 1.37–1.40 s。剩下最大的块是房东/恩主两条顺序贪心（Python 循环，约 0.2 s），以及交叉点两端按需查背景关系（0.22 s，compat 才需要；v1 模式 0.17 s）。
2. **房东分配的增量没起作用**：「在住户集合与街没变就沿用」21 年里一次也没命中；房东分配是全城按户键顺序的贪心，局部改动会顺序传下去，没做成精确的局部增量。同一口水的增量是精确的（每年只重算约 10% 的户）。
3. **制度分配要存**：房东/恩主/债是全城顺序贪心，单户自我网算不出来，所以批量算时存了它们的起止年区间（干山 11,095 条，户均 2.1）。这是除交叉点外唯一落盘的关系。
4. `pattern_hits` 口径与 v0 不同（v1 数「模式·年」57,741；v0 数有向 (模式, 甲, 乙) 7,879），不能直接比。
5. **新依赖**：numpy、scipy（沙箱原本没有 scipy，`pip install numpy scipy`）。
