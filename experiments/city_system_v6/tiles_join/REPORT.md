# CS 瓦片房屋 ↔ 账本 id 对接 + 户籍旁车（刘线）

对象：CS 线瓦片 <https://changsheng0804-blip.github.io/anthousa-hark-CS/living/tiles/>（meta.json + vec/{tx}_{ty}.json，131 个存在）。
账本：仓库根 `world.json`（18,943 栋）。制度：`../city_system.py`（v6，一户一职 + 行会）。不做前端。

**最重要的缺口：个体身份只在「年份对 + 约 5 单位邻域」内确定。** CS 房屋相对账本位置有逐栋扰动（中位 4.8 单位），
而账本相邻房屋间距约 1.5 单位。AF50 在世的已匹配房屋中，门限内同年份对候选中位 4 栋、p90 12 栋，唯一候选的只有 2,772/15,193。
所以匈牙利匹配给出的是一个总距离最小的一对一配对，不是可验证的个体对应。按字段看（AF50，门限内所有候选是否同值）：

| 字段 | 候选全部一致 |
|---|---|
| 区 d | 95.8% |
| 教区 | 91.8% |
| 供水组 | 89.7% |
| 行会 | 87.6% |
| 哨 | 80.1% |
| 坊 | **30.1%** |

即区/教区/供水组在瓦片上基本可信；坊和「这栋是否任职」取决于个体选择，对 CS 画面上的具体某栋只能视为示意。

## 方法

1. **读取与去重**：每栋 `[built, destroyed(9999=未毁), sortY, 轮廓16数, 部件]`，键 (built, destroyed, 轮廓前 4 数)。
   轮廓 16 数 = 8 点：前 4 点是平面轮廓，后 4 点是整体偏移约 (3.5, 2.5) px 的同形（推测为影子/屋顶），质心与面积只用前 4 点。
   片区：质心落入的第一个 `owner_order` 框。
2. **片区 ↔ 账本区（年份对分布）**：对每片区的年份对直方图与每区的直方图算余弦（join_stats.json `pair_cosine_d`）。
   结论是 **片区与账本区不是一一对应**：账本只有 5 区、CS 9 片区，forum 与 harbor 年份分布相近（余弦 0.9+）无法区分；
   匹配后实际落区（`matched_d`）：
   | 片区 | 匹配 | 落区 |
   |---|---|---|
   | nangang | 4,884/4,941 | harbor 3,150 · forum 1,648 · xerolophos 86 |
   | jinjiao | 3,037/3,058 | forum 3,037 |
   | gucheng | 5,327/5,354 | byzas 2,498 · forum 1,688 · harbor 1,141 |
   | siqiu | 2,901/2,963 | forum 2,812 · xerolophos 89 |
   | dongjia | 730/730 | byzas 730 |
   | xipo | 618/630 | xerolophos 609 · harbor 9 |
   | qiangwai | 360/380 | harbor 360 |
   | jiaowan | 169/171 | forum 169 |
   | nanan | 125/146 | harbor 120 · byzas 5 |
   因此没有把「片区→区」作为匹配约束，区由匹配到的账本房屋带出。
3. **变换**：两侧年份对都唯一的房屋作锚点（395 个，gucheng 311、nangang 48、dongjia 23，其余片区 0–6 个）。
   全城 RANSAC 仿射内点 388/395，结果近似纯平移 + 等比缩放：账本 ≈ CS_px / 14.2 + (415.5, 195.4)，x/y 比例 14.14/14.44（meta.scale 14.22），剪切 < 0.0003。
   第一轮用全城变换匹配后，每片区用「门限内唯一候选」的匹配对（不用歧义匹配，避免自我强化）做 RANSAC + 相似变换重拟合，样本 < 30 的片区（qiangwai 19、jiaowan 18、nanan 14）沿用全城变换；迭代 2 次。
4. **匹配**：每个年份对内，变换后欧氏距离（账本单位）做匈牙利匹配，门限 12 单位（锚点最大残差约 9.6）。
5. **旁车**：`city_system.build(world, Y)` 在账本坐标里算 AF40/50/60 制度，再按账本 id 连到瓦片。

它是逐栋的布局扰动，不是片区级的拼贴偏移，再精细的变换也消不掉。

### 轮廓面积抽查（20 栋，CS 面积 / scale² ÷ 账本面积）

比值 0.29–1.01，中位约 0.6（全部匹配：中位 0.608，p10 0.403，p90 0.892）。量级合理（CS 房屋略小），但
**CS 面积与账本面积的相关系数 0.02**（锚点上的长边、朝向也不相关）：CS 房屋轮廓是另行生成的，不承载账本房屋形状，不能用作匹配特征。
明细见 join_stats.json `area_sample`。

## 旁车格式

`reg/{Y}/{tx}_{ty}.json`：`{"Y":50,"f":["id","d","fang","parish","water","watch","guild","office"],"h":[…]}`，`h` 与 vec 瓦片 `h` 同序：
- `null`：未匹配；`["h123"]`：已匹配但该年不在世（vec 瓦片三年共用，含各年房屋）；
- 否则 `[账本id, 区, 坊, 教区, 供水组, 哨, 行会, 职务]`；教区若同属阿里乌教区则为 `[教区, 阿里乌教区]`；职务 `0` 或 `[职名, 节点键]`（如 `["坊长","坊:d_forum#f12"]`）。

| Y | 有户籍记录 | 已匹配不在世 | 未匹配 | 账本在世 | 瓦片内任职户 / 全城职位 |
|---|---|---|---|---|---|
| 40 | 10,661 | 7,490 | 222 | 10,713 | 131 / 132 |
| 50 | 15,193 | 2,958 | 222 | 15,296 | 149 / 150 |
| 60 | 16,449 | 1,702 | 222 | 16,577 | 151 / 152 |

## 缺口

- **CS 坐标不是可用的空间坐标**：与「9 片区拼贴」的说法不同，实测各片区落在同一个全城平移 + 缩放上（片区框只是渲染区域），
  但叠了逐栋约 5 单位的扰动。两种情况结论一样：空间制度（坊、供水组、教区、哨）只能在账本坐标里算，再按 id 连接；不能在瓦片坐标上重算。
- **个体歧义**：见上表；坊与任职标记在瓦片上是示意级。要做到个体可信，需要 CS 在 vec 里写入账本 id（最省事），或保留账本质心。
- **只有 AF40/50/60**：CS 瓦片只烤了这三年；其他年份旁车可同法即时生成（单年 < 0.5 s），但没有对应画面。
- **未匹配 222 栋 CS**：169 栋是 CS 某年份对栋数多于账本（CS 多出的房屋，原因在 CS 线），53 栋同年份对候选都在 12 单位门限外。
- **账本缺席 792 栋**：664 栋三年均不在世（含 d_exokionion 全部 531 栋，建于 AF61+），128 栋在世但未进入匹配（与上面的超额/门限外互为另一面）。
- 账本中 AF40/50/60 在世却不在瓦片上的：52 / 103 / 128 栋（standing_ledger − 有记录）。

## 文件

- `load.py` 拉取/读取 CS meta 与 vec（缓存 /tmp/vec）；`join.py` 对接 → `join.json`（每瓦片顺序的账本 id）、`join_stats.json`；
- `stability.py` → `stability.json`（字段稳定度）；`bake.py` → `reg/{40,50,60}/*.json`、`bake_stats.json`。
- 复现：`python3 join.py && python3 stability.py && python3 bake.py`。
